# When outputs are text, byte-identity is a perfect oracle

**Claim.** If a pipeline's output is a file, the strongest equivalence oracle available is byte-for-byte comparison against a reference regeneration — zero tolerance, zero flakiness, zero sampling. Where it applies, it replaces the entire scenario-inventory machinery: two runs that produce identical bytes are equivalent by definition, and a single differing byte is a complete, localizable failure report.

**Why.** Behavioral oracles for programs must decide *which observations matter* (stdout? exit code? file writes? order?) and then tolerate the rest — that decision is where oracles leak. Text outputs have no such ambiguity: every byte is observable and all of them matter. `diff` is total (it never says "equivalent enough"), deterministic (same inputs, same verdict), and its failure output *is* the diagnosis. An equivalence gate built on byte-identity cannot be argued with, tuned, or gradually relaxed — the properties that make behavioral oracles drift into rubber stamps.

**Failure example (the positive case).** A research atlas publishes pages compiled from researcher journals. Hand-editing a published page is the classic silent-corruption path: the page drifts from its evidence, and nothing fails. The fix was not a review rule but an oracle: CI regenerates every page from the public journals on each push and diffs against the committed pages. The regeneration was first verified byte-identical by hand (twice, including after a generator change), so any future difference is, by construction, a hand-edit or a generator bug — both of which should fail the build. The gate's strength is that it has no threshold to negotiate.

**Method.** Use byte-identity wherever the artifact is regenerable from public inputs: generated sites, compiled docs, lockfiles, serialized schemas, SVG produced from data. Three conditions make it honest: (1) the generator is deterministic — no timestamps, no hash-order iteration, no locale-dependent formatting in the output; (2) the inputs are the committed ones (the journals, the data file), not the environment; (3) the identity claim was verified once by an independent check before the gate went live, so the gate enforces a known-true invariant rather than freezing an unknown state. Then wire it into CI as a hard fail, and publish the regeneration command so strangers can run the same oracle.

**Counter-note.** Byte-identity is brittle *by design*, and brittleness is wrong when differences are legitimate: formatting-only churn, dependency-version drift in generated headers, or outputs that legitimately embed dates will fail the gate forever and train people to bypass it. In those cases either normalize before comparing (canonicalize, strip volatile fields — and say exactly what you stripped) or fall back to a behavioral oracle. The rule: byte-identity where any difference is a bug; normalized comparison where some differences are features; behavioral oracles where the output is not a file at all.
